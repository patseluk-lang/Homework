# Система реєстрації користувачів та їхніх акаунтів на сайтах

Навчальний проєкт із двох частин:

| Файл | Що це |
|---|---|
| `users_app.py` | базове завдання: реєстрація та вхід, модуль `sqlite3` |
| `users_app_mysql.py` | розширене завдання: MySQL, перевірка дублікатів, таблиця сайтів |

---

## Частина 1. Базова версія (`sqlite3`)

- реєстрація користувача (`username`, `password`, `email`);
- вхід у систему з перевіркою даних у базі;
- валідація введення: порожні значення та формат email;
- обробка помилок: дублікат `username`, дублікат `email`, помилки БД;
- текстове меню в консолі.

Сторонні бібліотеки не потрібні:

```bash
python users_app.py          # інтерактивне меню
python users_app.py --demo   # автоматична перевірка на тестових користувачах
```

Режим `--demo` виконує пункт умови «перевірте вашу реалізацію, створивши кілька
тестових користувачів»: реєструє трьох користувачів, показує обидві помилки
валідації, обидві помилки дублікатів і три сценарії входу. Працює з окремою
базою `demo_users.db`, тому робочу `users.db` не чіпає.

### Структура таблиці `users`

| Поле | Тип | Обмеження |
|---|---|---|
| `id` | INTEGER | PRIMARY KEY, AUTOINCREMENT |
| `username` | TEXT | NOT NULL, UNIQUE |
| `password` | TEXT | NOT NULL |
| `email` | TEXT | NOT NULL, UNIQUE |

## Частина 2. Розширена версія (MySQL)

### Що додано

1. **Перевірка дублікатів логінів та email** — обома способами одночасно.
2. **Таблиця `sites`** із зовнішнім ключем на `users.id` та класом `SiteAccount`.
3. **Кабінет користувача**: після входу можна додавати сайти й переглядати їх список.

### Встановлення

```bash
pip install -r requirements.txt
```

Потрібен запущений сервер MySQL. Параметри підключення задаються змінними
оточення (у коді лишені лише значення за замовчуванням):

```bash
export DB_HOST=localhost
export DB_PORT=3306
export DB_USER=root
export DB_PASSWORD=secret
export DB_NAME=users_app

python users_app_mysql.py
```

Базу та обидві таблиці програма створює сама при першому запуску.

### Структура бази

**Таблиця `users`**

| Поле | Тип | Обмеження |
|---|---|---|
| `id` | INT | PRIMARY KEY, AUTO_INCREMENT |
| `username` | VARCHAR(50) | NOT NULL, UNIQUE |
| `password` | VARCHAR(255) | NOT NULL, `COLLATE utf8mb4_bin` |
| `email` | VARCHAR(100) | NOT NULL, UNIQUE |

**Таблиця `sites`**

| Поле | Тип | Обмеження |
|---|---|---|
| `id` | INT | PRIMARY KEY, AUTO_INCREMENT |
| `user_id` | INT | NOT NULL, FOREIGN KEY → `users(id)` ON DELETE CASCADE |
| `site_name` | VARCHAR(100) | NOT NULL |
| `login` | VARCHAR(100) | NULL — для входу через сервіс |
| `password` | VARCHAR(255) | NULL — для входу через сервіс |
| `login_type` | VARCHAR(20) | NOT NULL (`google`, `apple`, `facebook`, `інша`) |

Додатково: `UNIQUE (user_id, site_name, login_type, login)`.

### Регістр і порівняння рядків

База створюється з `utf8mb4_unicode_ci`, тому `username` та `email`
порівнюються без урахування регістру: `Vasyl` і `vasyl` — той самий користувач.
Перевірка дублікатів у Python використовує `casefold()`, щоб обидва способи
давали однаковий результат.

Пароль — навпаки: колонка `users.password` оголошена з `COLLATE utf8mb4_bin`,
інакше при вході `Secret` збіглося б із `secret`. Якщо таблиця вже створена
попередньою версією, `CREATE TABLE IF NOT EXISTS` її не змінить — базу треба
перестворити або виконати `ALTER TABLE`.

### Два способи перевірки дублікатів — порівняння

| | Спосіб 1: `UNIQUE` у SQL | Спосіб 2: перевірка в Python |
|---|---|---|
| Де спрацьовує | у базі, під час `INSERT` | до `INSERT`, окремим `SELECT` |
| Надійність | абсолютна: база не пропустить дублікат навіть при одночасних запитах | не захищає від гонки запитів між `SELECT` і `INSERT` |
| Навантаження | один запит | два запити, вибирає всі логіни й пошти в пам'ять |
| Повідомлення | треба розібрати ім'я ключа з тексту помилки | одразу видно, що саме зайняте — і можна назвати обидва поля разом |

**Обрано обидва разом.** `UNIQUE` — як гарантія цілісності даних, перевірка в
Python — як зручний зрозумілий діалог з користувачем. Це стандартна практика:
код пояснює, база страхує.

Дві важливі деталі:

- у способі 2 логіни та пошти складаються в **окремі** множини. Одне й те саме
  значення може бути логіном одного користувача та поштою іншого, тому змішувати
  колонки не можна;
- у способі 1 з тексту помилки береться **ім'я порушеного ключа**
  (`for key '...'`), а не просто підрядок з усього повідомлення. Інакше email
  на кшталт `admin_username@example.com` дав би неправильне пояснення помилки.
  MySQL 8 пише `users.username`, MariaDB — `username`, тому ключ порівнюється
  закінченням.

### Клас `User`

| Метод | Призначення |
|---|---|
| `__init__(username, password, email)` | ініціалізує користувача |
| `find_duplicates(username, email)` | перевірка дублікатів засобами Python |
| `register()` | зберігає користувача в базу, повертає `True` / `False` |
| `login(username, password)` | перевіряє дані, повертає `True` / `False`, запам'ятовує `id` |

### Клас `SiteAccount`

| Метод | Призначення |
|---|---|
| `__init__(user_id, site_name, login_type, login, password)` | ініціалізує запис про сайт |
| `save()` | додає запис у таблицю `sites` |
| `get_login_types(user_id, site_name)` | які види входу вже збережені для сайту |
| `get_all(user_id)` | усі сайти користувача |
| `show_all(user_id)` | виводить сайти на екран таблицею |

### Логіка видів входу

Якщо обрано `google`, `apple` або `facebook` — логін і пароль **не запитуються**,
у базу пишеться `NULL`: вхід відбувається через сервіс, і власних облікових
даних на сайті просто не існує.

Логін і пароль питаються лише для виду `інша`. Кілька різних акаунтів на одному
сайті дозволені (робочий і особистий), а от той самий логін двічі — ні: за це
відповідає `UNIQUE (user_id, site_name, login_type, login)`.

Окрема деталь: у SQL два `NULL` не вважаються рівними, тому для соціальних видів
входу цей `UNIQUE` не спрацьовує. Повтор `google` для того самого сайту
перевіряється явним запитом у `SiteAccount.save()`, а не лише в меню, — щоб
захист працював і при програмному виклику класу.

## Технічні деталі

- Усі запити з даними користувача параметризовані (`?` у sqlite3, `%s` у MySQL) —
  захист від SQL-ін'єкцій.
- Ім'я бази підставляється в `CREATE DATABASE` напряму (параметризувати його не
  можна), тому воно перевіряється регулярним виразом і береться у зворотні лапки.
- Робота зі з'єднанням винесена в контекстний менеджер: коміт при успіху, відкат
  при помилці, закриття завжди. Це важливо саме для `sqlite3`: `with conn:`
  керує транзакцією, але з'єднання **не закриває**.
- Кодування бази — `utf8mb4`, тому назви видів входу українською зберігаються коректно.
- Таблиці `InnoDB` — інакше зовнішній ключ не працюватиме.
- Ширина колонок у списку сайтів рахується за найдовшим значенням, тому довгі
  назви не ламають таблицю.
- `Ctrl+C` та `Ctrl+D` завершують програму повідомленням, а не трасуванням стека.

## Перевірка

Базова версія перевіряється вбудованим режимом `python users_app.py --demo`.

MySQL-версію перевірено скриптом `check_mysql.py` на MySQL 8.4.11
(`mysql-connector-python` 26.7.0): 15 перевірок, усі пройдено. Скрипт працює з
окремою базою `users_app_check` і видаляє її за собою.

```bash
export DB_HOST=localhost DB_PORT=3306 DB_USER=root DB_PASSWORD=secret
python check_mysql.py
```

## Обмеження

Паролі зберігаються у відкритому вигляді — так вимагає умова навчального
завдання. У реальному застосунку пароль користувача слід зберігати як
криптографічний хеш (`bcrypt`, `argon2`), а паролі сторонніх сайтів — у
зашифрованому сховищі.
