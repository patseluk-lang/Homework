# Система керування інтернет-магазином

Навчальний проєкт на Python, що демонструє застосування семи патернів проєктування
GoF у межах однієї предметної області — обробки замовлення в інтернет-магазині.

- `Online_store_management_system.py` — уся система + демонстраційний сценарій `main()`
- `test_shop.py` — 20 тестів на `pytest`

## Запуск

```bash
python Online_store_management_system.py   # демонстрація
pytest -q                                  # тести
```

Залежності, крім `pytest`, відсутні — використано лише стандартну бібліотеку.

## Модель предметної області

Замовлення (`Order`) має номер, покупця, список товарів, спосіб оплати, спосіб
доставки, поточний стан і історію виконаних команд. Магазин (`Shop`) створює
замовлення та автоматично підписує на них наперед задані канали сповіщень.

Гроші скрізь рахуються в `Decimal` (функція `money()` округлює до копійок за
`ROUND_HALF_UP`). `float` для цін не використовується свідомо: `0.1 + 0.2 != 0.3`
у двійковому представленні, і на ланцюжку з чотирьох націнок похибка стає видимою
в чеку. Статуси замовлення винесені в `Enum` — це унеможливлює порівняння з
рядком-опискою.

## Використані патерни й обґрунтування

### 1. Factory — `ProductFactory`

Створює `SimpleProduct`, `DigitalProduct`, `SubscriptionProduct` за рядковим
ключем.

**Чому:** типи товарів мають різні конструктори (вага / розмір у МБ / кількість
місяців), але клієнтський код працює з ними однаково — як із `Product`. Без
фабрики кожне місце створення товару містило б ланцюжок `if kind == ...`. Тут
реєстр `_registry` + метод `register()` дозволяють додати новий тип
(наприклад, подарункову картку) **не змінюючи** жодного рядка існуючого коду —
це принцип відкритості/закритості в чистому вигляді.

### 2. State — `NewState`, `ProcessingState`, `ShippedState`, `DeliveredState`, `CancelledState`

Замовлення делегує `pay()`, `ship()`, `deliver()`, `cancel()` поточному об'єкту стану.

**Чому:** правила переходів між статусами — це найбільш «розгалужена» частина
логіки: доставлене замовлення не можна відправити повторно чи скасувати, нове не
можна відправити до оплати. Реалізація через `if/elif` за статусом дала б один
величезний метод, який доводиться правити при кожному новому статусі. У State
кожен стан — окремий клас, а базовий `OrderState` за замовчуванням **забороняє**
все (`_deny`), і кожен нащадок відкриває лише свої переходи. Дозволена дія — це
явно перевизначений метод, тому забути заборону неможливо.

### 3. Strategy — оплата й доставка

Два незалежні сімейства: `CardPayment` / `PayPalPayment` / `CryptoPayment` та
`CourierDelivery` / `PostDelivery` / `PickupDelivery`.

**Чому:** спосіб оплати й спосіб доставки — це взаємозамінні алгоритми, які
обираються **під час виконання** й можуть змінюватися протягом життя замовлення
(див. `ChangeDeliveryCommand`). Замовлення знає лише інтерфейс (`pay()`,
`describe()`) і не залежить від конкретної платіжної системи. Додати Apple Pay —
означає додати один клас.

### 4. Observer — `Publisher`, `EmailNotifier`, `SmsNotifier`, `AdminNotifier`

`Order` успадковує `Publisher` і розсилає подію `Event` при кожній зміні статусу
та при явному повідомленні.

**Чому:** кількість каналів сповіщення — це те, що змінюється найчастіше, і
замовлення не повинно про них знати взагалі. Підписка/відписка динамічна: у
демонстрації SMS-канал відключається посеред життєвого циклу, і решта каналів це
не зачіпає. Подія передається як об'єкт `Event` (`dataclass`) зі старим і новим
статусом, тож кожен канал сам вирішує, що показати користувачеві: `Admin` друкує
технічний перехід, `Email` — нейтральний текст.

### 5. Decorator — `Discount`, `PromoCode`, `GiftWrap`, `Insurance`

Ціна — це ланцюжок: `BasePrice` → знижка → промокод → пакування → страхування.
Кожен елемент реалізує `PriceComponent.total()` і обгортає попередній.

**Чому:** додаткові послуги комбінуються в довільному порядку й довільній
кількості, а порядок впливає на результат (знижка 10% до промокоду і після нього —
різні суми). Створювати клас під кожну комбінацію нереально, а список «модифікаторів»
із ручним підсумовуванням втратив би порядок застосування. Ланцюжок декораторів
зберігає порядок природно, дає безкоштовний деталізований чек (`price_report()`
просто проходить ланцюжком) і безкоштовне скасування — `remove_last_extra()`
знімає верхню обгортку.

### 6. Command — `CommandQueue` + `undo`

`CreateOrderCommand`, `PayOrderCommand`, `ChangeDeliveryCommand`,
`AddExtraCommand`, `SendNotificationCommand`, `CancelOrderCommand`.

**Чому:** дії потрібно було не просто виконати, а **накопичити в черзі** й
виконати послідовно, а потім скасувати у зворотному порядку. Це неможливо без
перетворення дії на об'єкт: команда зберігає всі аргументи та попередній стан
(`_prev_state`, `_prev_method`, `_prev_paid`), тож `undo()` відновлює саме те, що
було, а не «щось схоже». Історія лежить у самому замовленні (`remember()` /
`undo()`), тому скасування працює і поза чергою.

Окремо: `OrderRef` — тримач посилання на замовлення. Він потрібен тому, що всі
команди додаються в чергу **до** того, як замовлення взагалі створене; перша
команда заповнює `ref.order`, наступні читають. Це дозволило обійтися без
перевірок «а чи вже існує замовлення» в кожній команді.

`SendNotificationCommand` свідомо не потрапляє в історію undo: надіслане
повідомлення технічно не відкликається, і робити вигляд, що воно відкликається,
було б брехнею інтерфейсу.

### 7. Singleton — `Logger`

**Чому:** лог має бути один на всю програму, інакше записи розповзаються по
незалежних об'єктах і хронологію не відновити. Реалізовано через `__new__`, а не
через глобальну змінну, щоб будь-який виклик `Logger()` у будь-якому модулі
повертав той самий екземпляр без передавання його параметром через усі класи.

## Тести

20 тестів покривають ключові точки, де помилка найімовірніша:

| Група | Що перевіряється |
|---|---|
| Factory | створення всіх типів, помилка на невідомому типі, реєстрація нового типу |
| Decimal | ціна є `Decimal`, ланцюжок націнок дає точні суми |
| Decorator | результат кожного кроку ланцюжка, промокод не опускає суму нижче нуля |
| State | оплата без способу оплати, повний життєвий цикл, заборони для доставленого замовлення |
| Command / undo | відкат послуги, доставки, оплати; undo на порожній історії не падає |
| Observer | підписка й відписка, кількість отриманих подій |
| Singleton | `Logger() is Logger()` |
